# Google Play checklist: name and description

Use this list before every publish or listing update. Tick each item. Mark an item "n/a" only with a reason.

## 1. Title (max 30 characters)

- [ ] Length is 30 characters or less (count it, spaces included).
- [ ] Contains the main search phrase once (for example "Bluetooth Keyboard").
- [ ] Reads like a name, not a list of keywords: `[Main phrase]: [qualifier]`.
- [ ] No ALL CAPS (except real acronyms such as HID), no emoji, no special symbols for decoration.
- [ ] No claims: "best", "#1", "top", "free", "new", "official", "no ads", "sale".
- [ ] No other company or app names (KeePass, Stream Deck, Logitech and so on) and no look-alike of a known brand.
- [ ] Says what the app is. A stranger understands the category from the title alone.
- [ ] Matches the name under the icon and in the app (a short launcher name is fine, but not misleading).
- [ ] Searched Google Play for the title: there is no confusingly identical app name.

## 2. Short description (max 80 characters)

- [ ] 80 characters or less, one sentence.
- [ ] Formula: what the phone becomes + the main use + one differentiator ("No PC software").
- [ ] Does not repeat the title word for word, but adds a second search phrase (macro pad, password sender).
- [ ] No claims, no emoji spam, no call to action like "Download now" or "Rate 5 stars".
- [ ] Every statement is true in the current build.

## 3. Full description (max 4000 characters, aim for 1500 to 2200)

Structure
- [ ] First 2 to 3 lines work alone: they repeat the title phrase once, say what the app does and name the key differentiator. Only these lines show before "Read more".
- [ ] Then 3 to 6 short sections with plain headers and bullets in the form "Feature: benefit".
- [ ] A compatibility and requirements block: Android version, supported hosts, known limits.
- [ ] No step-by-step instructions (keep them for the app, a website or the README).
- [ ] No separate keyword list. Search terms appear only in natural sentences.

Search wording
- [ ] Each main phrase (Bluetooth keyboard, macro pad, password sender) appears about 2 to 3 times, not more.
- [ ] Phrases match what users type, not internal terms (say "Bluetooth keyboard", not only "HID device").
- [ ] Synonyms are used naturally: phone as keyboard, wireless keyboard, shortcuts, macros.

Truth and policy
- [ ] Every feature in the text exists in the release build. Open the app and check each bullet.
- [ ] Nothing is promised that depends on another app (for example "Send via HID" in the KeePass fork) unless that app is released.
- [ ] Claims about hosts (Windows, Linux, macOS, Android TV) were tested at least once, or are worded as "any device that accepts a Bluetooth keyboard".
- [ ] Limits are stated honestly: keyboard only, Mouse Keys works on Windows, HID profile support varies by phone.
- [ ] No superlatives or ranking claims ("best", "only", "number one"), no rating or review requests, no fake awards or user counts.
- [ ] No other brands used as keywords. Third-party names appear only as plain compatibility facts and only if needed.
- [ ] No excessive emoji, capital letters or repeated symbols. Emoji only on section headers if used at all.
- [ ] No misleading or irrelevant text, no contact or promo spam, no text meant only for search.
- [ ] The text does not claim security guarantees you cannot prove (for example "unhackable").

Readability
- [ ] Paragraphs are 1 to 3 lines. Bullets are one line each.
- [ ] No long lists of shortcuts or commands. Users want the benefit, not the reference.
- [ ] Read it once on a phone in the Play Console preview. Is it clear in 10 seconds?
- [ ] Spell check passed, and a native English reader read it.

## 4. Consistency with the rest of the listing

- [ ] Icon, screenshots and feature graphic show only features that really exist (no mouse touchpad if there is none).
- [ ] Screenshot captions use the same words as the description.
- [ ] Data safety form matches the app: Bluetooth, local network web server, crash reporting if enabled.
- [ ] A privacy policy URL is set and describes the same data handling.
- [ ] Permissions requested by the app are explained by features in the description (Bluetooth, notifications, foreground service).
- [ ] The category and tags match the title (Tools or Productivity).

## 5. How to validate quality

1. **Count**: paste title, short and full text into a character counter. Check limits.
2. **Truth test**: for every sentence write which screen or code proves it. Remove any sentence without proof.
3. **Competitor read**: compare with 5 top apps in the niche. Same order of ideas, but not copied text. No unique claims that you cannot support.
4. **Stranger test**: show the title and short description to a person. Ask what the app does and who needs it. If the answer is wrong, rewrite.
5. **Search test**: search the main phrases on Google Play. Check that your title reads naturally next to the results.
6. **Policy scan**: read the Google Play Metadata policy (store listing and promotion) and Impersonation policy once per release. Compare the text with the policy list.
7. **Preview**: open the Play Console preview on a phone and a tablet.
8. **After publishing**: wait 1 to 2 weeks and check Play Console, Store listing statistics (impressions, installs per search term). Change one thing at a time. Use store listing experiments for the icon, short description and screenshots.

## 6. Rejection and warning risks (quick scan)

- Keyword stuffing or lists of search terms.
- Words like "best", "#1", "free" or price and promotion text in the title or icon.
- Brand names of other companies used for search.
- Repeated or heavy emoji and capital letters.
- Reviews, ratings or install counts quoted in the text.
- A description that does not match the real app behaviour.
- Claims about capabilities that need extra software or hardware but are not explained.
