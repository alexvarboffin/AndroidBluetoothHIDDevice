# Баг и задача: «залипшая» клавиша и удержание клавиш (KeyDown / KeyUp)

Статус: описание проблемы и требования к решению. Код ещё не написан.
Связано с `Documentation/Roadmap.md`, раздел «Future: одновременные клавиши и удержание».

## 1. Что случилось (баг)

Пользователь наблюдал на ПК с Windows бесконечный ввод одного символа: `dddddddddddddddddddddd`. Ввод остановился только после того, как он выключил Bluetooth на ПК.

Это значит, что хост получил HID-отчёт «клавиша `d` зажата» и не получил отчёта «клавиша отпущена». Windows считает клавишу зажатой, пока она есть в последнем полученном отчёте, и сама включает автоповтор.

### Вероятная причина

Процесс приложения на телефоне упал (или был убит системой), пока клавиша была зажата, а Bluetooth-соединение с ПК осталось живым. Это не штатный разрыв:
- При штатном закрытии соединения (выключили Bluetooth, закрыли HID-профиль) стек HID на хосте сбрасывает состояние клавиш, и «залипание» обычно не возникает.
- Если приложение упало или зависло, а радио и линк формально живы, хост не считает устройство отключённым до таймаута линка (секунды и больше). За это время последний отчёт с зажатой клавишей остаётся в силе, и идёт автоповтор.

Из этого следует главное: полагаться на то, что Windows сама отпустит клавишу при потере связи, нельзя. Защита должна быть на стороне приложения.

Это предположение, а не доказанный факт: точный сценарий падения не воспроизводился. Нужно проверить воспроизведением (см. раздел 5).

## 2. Как HID представляет «нажатие» и «удержание»

HID-клавиатура шлёт хосту не события, а состояние. Каждый отчёт говорит: «сейчас зажаты такие модификаторы и такие клавиши».
- Клавиша зажата, пока она есть в последнем отчёте.
- Клавиша отпущена, когда пришёл отчёт, где её нет (пустой отчёт отпускает всё).

Поэтому:
- Тап = два отчёта подряд: отчёт с клавишей и пустой отчёт. Именно так сейчас работает `sendKey` в `HidDeviceManager.kt`.
- Удержание = один отчёт с клавишей, затем пауза без новых отчётов, затем пустой отчёт. Автоповтор и ускорение Mouse Keys включает сам хост. Периодически слать отчёты не нужно.

Отдельного API для «удержания» нет, отличие только в том, когда уходит пустой отчёт.

## 3. Проблема, которая привела к задаче

Кнопки Mouse Keys (Type tab, карточка «Mouse keys (Windows)») при удержании повторяют пару «нажал, отпустил» каждые 60 мс. Для Windows это серия отдельных тапов. Разгон курсора Mouse Keys при этом не включается, потому что он зависит от непрерывного удержания клавиши. С физической клавиатуры курсор разгоняется.

Решение этой проблемы (настоящее удержание) вводит риск из раздела 1: после отправки отчёта с зажатой клавишей пустой отчёт обязан дойти до хоста.

## 4. Требования к решению

Нельзя менять HID-дескриптор: режим остаётся keyboard-only. Не удалять закомментированный код и существующие функции.

1. Ввести в `HidDeviceManager` состояние зажатых клавиш и методы `keyDown(keyName, modifier?)` и `keyUp()` (или `releaseAll()`). Отправка идёт через `typingExecutor`, не с UI-потока.
2. Таймаут-страховка. После `keyDown` взвести таймер (порядка 3 секунд). Если `keyUp` не пришёл, менеджер сам шлёт пустой отчёт. Пока палец на кнопке, таймер продлевается (heartbeat из UI не нужен, достаточно продлевать при активных событиях). Нужно учесть, что долгое удержание Hold остаётся возможным.
3. Пустой отчёт при любой потере контроля: отпускание пальца, отмена жеста, смена вкладки, уход экрана с `STOPPED` / `onPause`, `onCleared` у ViewModel, остановка сервиса, отключение устройства и перед первым действием после нового подключения.
4. Пустой отчёт отправлять с небольшим повтором (например, дважды с паузой в десятки миллисекунд), чтобы одна потерянная посылка не оставила клавишу зажатой.
5. Обработать падение процесса. Если приложение убито, ни таймер, ни отпускание не выполнятся. Компенсировать нечем, кроме короткого окна между `keyDown` и таймаутом, поэтому таймаут выбирать минимальным, который не ломает сценарии. Если можно, зарегистрировать отпускание в слое, который живёт дольше UI (сервис / менеджер), а не в Composable.
6. Тап (`sendKey`) оставить как есть: два отчёта подряд.

## 5. Тесты

### 5.1. Тестовый метод

Добавить в `HidDeviceManager` метод `pressKeyFor(keyName: String, holdMs: Long, modifier: String? = null)`: `pressKey`, ожидание `holdMs`, затем `releaseKey`. Вызывать с `typingExecutor` или отдельного потока, не с UI. Для ручной проверки добавить отладочную кнопку на вкладке Type (можно скрыть за флагом debug), где `holdMs` задаётся полем или случайно в диапазоне 250-500 мс.

Пример: `pressKeyFor("A", Random.nextLong(250, 501))`. Ожидаемый результат сравнивается с `sendKey("A")`.

Важно: порог автоповтора задаёт хост. В Windows это «Задержка перед началом повтора» (Панель управления, Клавиатура), по умолчанию около 500 мс. Поэтому на границе 500 мс результат нестабилен, и тесты ниже используют значения с запасом. Перед тестами записать значение задержки и скорости повтора на ПК.

Подготовка: подключить телефон к ПК, открыть Блокнот в фокусе, включить в приложении вкладку Type.

### 5.2. Ручные тесты на хосте (Блокнот)

| № | Действие | Ожидаемый результат |
|---|----------|---------------------|
| T1 | `sendKey("A")` | Один символ `a`. Эталон. |
| T2 | `pressKeyFor("A", 100)` | Один символ `a`, как в T1. |
| T3 | `pressKeyFor("A", 250..500)` в 20 попытках | Один символ в каждой попытке, если задержка повтора на ПК не меньше 500 мс. Если появляются двойные символы, зафиксировать задержку на ПК. |
| T4 | `pressKeyFor("A", 2000)` | Один символ сразу, затем автоповтор после задержки хоста, всего заметное количество символов. После 2000 мс повтор прекращается. |
| T5 | `pressKeyFor("A", 2000)` и сразу `sendKey("B")` | После окончания удержания `b` печатается один раз, `a` не повторяется. |
| T6 | `pressKey("A")` без `releaseKey` | Через время таймаута-страховки (около 3 с) повтор прекращается сам. Это проверка таймаута. |
| T7 | Модификатор: `pressKeyFor("TAB", 300, "ALT")` | Alt+Tab переключает окно, Alt отпущен. |

### 5.5. Регрессия

- Скорость набора текста и пресетов не изменилась (тест на строке из 200 символов, замер до и после).
- `sendKey` и `sendKeyComboBlocking` работают как раньше (`Ctrl+Alt+Del`, пресеты Windows).
- Дескриптор HID не менялся (`git diff` по `HidDeviceManager.kt` не затрагивает массив дескриптора).
- Сборка проходит, `:app:compileDebugKotlin` успешен.

### 5.6. Автотесты (по возможности)

Вынести формирование отчётов в чистую функцию и покрыть unit-тестом: `pressKey("A")` формирует отчёт `[mod, 0, 0x04, 0, 0, 0, 0, 0]`, `releaseKey()` формирует нулевой отчёт, `pressKeyFor` вызывает пару в правильном порядке, а таймаут-страховка вызывает `releaseKey` по таймеру (на тестовом планировщике).
## 6. Открытые вопросы

- Какое значение таймаута допустимо для обычных сценариев, и нужно ли дольше для Hold.
- Нужен ли отдельный флаг «клавиши зажаты» в `uiState`, чтобы показать пользователю состояние.
- Можно ли на стороне Android узнать, что соединение «зависло», раньше, чем это сделает хост (например, сбой `sendReport`).
